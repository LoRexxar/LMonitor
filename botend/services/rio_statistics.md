# 魔兽世界数据观察：维护说明

页面入口：`/portal/rio-statistics/`。功能包含统计总览、完成记录、大秘境热力图和团本进度，复用现有 Portal 导航、主题与中央中文资料，不提供 CSV 下载。

## 首次启用

1. 安装地图拼接依赖：`python -m pip install -r requirements-rio-statistics.txt`。
2. 按项目正常流程执行 `python manage.py migrate`，应用新增导航迁移；不批量执行其他历史数据更新命令。
3. 在业务数据库配置唯一活跃的 `SeasonMeta`，绑定有效的 `rio_season` 和正式服构建版本。正式服 `WowTalentVersion` 及中文手册发布共同参与范围标识，不按来源日期猜测当前赛季。
4. 重启 Web 和后台采集进程，加载新增插件及夜间队列。后台会按默认配置登记 `RioStatisticsMonitor`，保留既有插件编号。
5. 已有统计缓存可执行 `python manage.py check_rio_statistics --deep --migrate --backup`，再执行 `python manage.py rebuild_rio_statistics_views`。首次没有元数据和快照时由后续采集准备；页面不会在访客请求中构建数据。

## 自动更新

北京时间每日 00:00 生成当日批次。数据观察首次启动限定在 00:00–06:00，当天已启动的未完成批次全天可补跑，复用租约和续租；其他长任务保留全天领取能力。00:00–06:00 优先长任务：有可领取或正在运行的自动长任务时，暂缓领取短任务；长任务均已完成或全部退避且没有运行者时，短任务可填补空档。06:00 起恢复两个短任务位，长任务共用一个任务位，不能借用空闲短任务位。跨过 06:00 时已有两个长任务的，允许完成当前执行，运行数降到零后才可领取下一个长任务，不强行中断。版本准备完成后，数据观察与人物/排名/聚合链凌晨可并行，各链内部串行。默认单轮最多 6000 次来源请求，硬上限 8000，包含元数据、重试和地图瓦片。

当天成功组合不重复采集。失败或中断最早三十分钟后续跑，跨过 06:00 也可恢复；429 遵守持久冷却，连续临时故障会熔断。预算不足、地图未齐、导入尚在生成、备份或展示发布失败都不能标记整轮完成。完成后数据库范围变化，可按新范围重新排队。

采集器在首个结果和后续每一百个结果处增量发布，并在轮次结束时补齐最后一批，导入命令也会维护展示文件。总览和默认 10–12 层范围优先；预算充足时先准备底图，空间数据不必等全部层数组合抓完才展示。数据库赛季或版本变化后接口立即停止使用旧范围；新范围未准备好时显示等待。已打开页面每分钟读取小状态，发现修订变化后更新当前结果并保留筛选。

## 存储与发布

默认数据根目录为 `var/rio-statistics/`，可由项目设置 `RIO_STATISTICS_ROOT` 指定。采集和 Web 进程必须访问同一数据根目录。本实现适用于同机多进程；不要直接将 SQLite 缓存库作为网络共享盘数据库使用。

- `snapshots.sqlite3`：独立缓存库，正文压缩并校验，正文、索引和轻量日历史同事务提交；业务赛季和任务仍在现有主数据库。
- 地图 WebP、瓦片断点和元数据目录：保留文件形式，地图严格匹配挑战模式编号、楼层和有向坐标边界。
- `views/current.json`：唯一原子发布指针，也是小状态来源。
- `views/catalog-a.json`、`catalog-b.json`：后台使用的全量双槽工作清单，公开请求不再打开它们。
- `views/reader-a.json`、`reader-b.json`：前端初始化与筛选校验用的轻量目录，提供代表范围及完整数量；保留各副本、三个指定层数范围和高级筛选。
- `views/indexes/<哈希前缀>-a.json`、`<哈希前缀>-b.json`：按键前两个十六进制字符分为最多 256 个索引分片，单项请求只定位自己的分片。
- `views/entries/<筛选摘要>-a.json`、`<筛选摘要>-b.json`：每组合双槽展示正文。

变化内容先写非活动槽并校验，最后原子切换指针。提交前失败保留上一完整发布；提交后中断时新发布已经完整。读者核对范围及正文标记，不读取未提交候选文件。旧 JSON 布局无删除迁移，首次升级保留旧展示文件。

同范围更新失败保留已有正文和真实采集时间；源缓存损坏时可继续保留已验证的同范围展示，标为旧数据并记录未完成。赛季、版本或周编号变化不跨范围借用旧数据。普通统计超过三十六小时标为旧数据；完整周热力图采用文末说明的自适应复核和八十四小时过期窗口。

公开 GET 只读轻量目录、对应索引分片及正文，不枚举统计库、不解压统计正文、不查询中文词条，也不解析全部历史组合的工作清单。仍检查业务数据库范围。API 每次校验版本并支持 ETag、304 和 gzip；地图为内容摘要地址，可长期缓存。不同缓存键的冷构建不占用同一把全局构建锁；单键仍合并重复构建。展示文件缺失或损坏时不在请求中回源或重建。

自动发布只处理本批改变的键并复用已提交正文；元数据的每日更新时间不再触发全部历史正文重建。管理员默认重建仍逐份校验，可用于修复损坏；旧布局快速升级使用下述复用选项。布局版本采用兼容字段，旧读取字段保留，但应更新并重启全部 Web 和后台采集进程，避免旧进程重新写回旧布局。

夜间执行深度检查和七个固定星期槽备份；来源限流或元数据失败时仍尝试本地维护。备份位于同一数据根目录，不能代替异机备份。默认全目录上限 10 GiB、磁盘最低可用 256 MiB，分别可由 `RIO_STATISTICS_MAX_STORAGE_BYTES`、`RIO_STATISTICS_MIN_FREE_BYTES` 配置。包括地图、旧文件、中间文件和备份，空间不足停止增长并保留有效数据，不自动删除文件。

## 命令

```powershell
# 当前范围总览试采
python manage.py sync_rio_statistics --modules overview --regions cn world --max-requests 8

# 指定热力图范围；地图首次准备也计入预算
python manage.py sync_rio_statistics --modules heatmaps --regions cn --dungeons den-of-nalorakk --levels 10-12 --periods season --max-requests 100

# 从已有统计库重建展示；不请求外网
python manage.py rebuild_rio_statistics_views

# 大目录快速升级：复用已提交且未改变的正文，不进行全量正文复核
python manage.py rebuild_rio_statistics_views --reuse-published

# 先查看最近批次卡在哪个阶段；不扫描全部正文或目录
python manage.py check_rio_statistics --progress-only

# 检查结构、正文、历史、展示、地图、容量和最近夜间批次
python manage.py check_rio_statistics --deep

# 首次迁移旧缓存并生成备份，保留原文件
python manage.py check_rio_statistics --deep --migrate --backup

# 导入已有授权来源的完成记录聚合响应
python manage.py import_rio_run_statistics C:/data/rio-runs.json
```

采集默认对未完成、冷却或忙碌状态返回非零退出码；主动进行部分试采可加 `--allow-partial`。巡检默认警告和错误均非零退出；明确允许已知警告时可加 `--allow-warning`，错误仍不放行。展示保留旧数据但来源尚未修复时，重建命令也报告未完成。

## 数据能力与限制

热力图与完成记录仅支持10–12层、16层及以上、20层及以上，不再提供单层或自选层数；热力图提供周区间、职业、专精、死亡者身份、已收录词缀、装等、用时和死亡数筛选。高级组合通过显式 CSRF 登记，由凌晨任务处理；不在访客 GET 中登记或获取来源数据，也不遍历所有维度的笛卡尔积。

完成记录目前只支持严格导入和夜间导入目录维护，没有配置自动获取新统计的上游来源，不自动抓取来源未公开的统计端点。默认导入目录为数据根目录 `imports/runs/`，可由项目设置 `RIO_STATISTICS_RUNS_SOURCE_DIR` 指定；夜间最多检查最新五十份 JSON 响应。巡检会明确提示缺少自动来源。

队伍组成、首领尝试等原站维度尚未实现，不宣称完整覆盖。角色数不等于现实独立玩家数，死亡热度不等于死亡概率，聚合网格不能还原逐把移动路线。空缺数据保持空缺。

## 2026-11-09 更新效率与调度调整

自动监控任务按北京时间分时领取：00:00–06:00 最多两个长任务并优先运行，长任务无可运行工作时允许最多两个短任务；06:00–24:00 最多一个长任务加两个短任务。跨时段已有任务自然完成，不撤销有效租约；过渡期间可能保留两个已运行长任务，但不再补充长任务。普通工作池固定三个工作者，另设游戏版本和数据观察专用工作者；空闲线程数不等于正在执行的任务数。人工执行仍沿用显式绕过自动排队的语义，快照维护线程也不计入这一监控任务配额。

赛季、游戏版本和地图工具准备仍是共同屏障。准备结束后，数据观察与人物/排名/聚合链在凌晨可以并行；后者保留原依赖顺序和未完成WCL周期恢复优先级。白天两条链共用一个长任务位；候选在工作者分流前统一选定，专用工作者也不能突破配额。需要重启全部后台进程才能统一采用新的领取规则；本轮未进行线上部署。

完整周热力图首次仍次日复核；与上一次成功结果完全一致时，下一次复核延后到三天，变化或错误后恢复日更。周编号和业务范围仍参与缓存身份，跨周与跨版本不能使用旧范围。完整周展示的过期窗口相应为84小时，其余仍为36小时。这里接受最多三天的迟到统计修正延迟；活动中的赛季累计数据仍日更，不把“昨天没变”当作“今天一定没变”。

正常维护将收尾完整性检查与备份内检查合用同一份结果，保留备份前校验。两次维护检查现在可复用同日、同内容的已验证正文证明，具体规则见文末。异常分支仍允许重新检查。日志新增数据观察业务结果、请求耗时和各阶段累计时间；备份阶段包含其内部完整性校验，网络耗时属于各阶段的子集，不可再次相加。

人物日更增加批内HTTP连接复用，记录按榜单、资料活动、队伍与Battle.net分类的请求数和累计耗时。天赋元数据每专精批次重新核对并共享；对输入和实际解析资料取内容摘要，持久化复用节点加工结果，不重复保存渲染布局。缓存最多保留每专精256项，使用既有私有压缩工作缓存和校验机制；缓存淘汰只影响计算量。资料齐全时不再逐人查询WCL回退，缺项回退必须匹配赛季、地区、服务器、人物、职业和专精。

首轮生产验收应核对：normalization_cache的hits/builds、http_summary的请求数与耗时、数据观察stage_seconds及业务完成状态、两条长任务是否重叠、排名与聚合是否仍按依赖顺序执行。本地语义测试不代表线上耗时已经下降，不预先承诺分钟数。

## 2026-11-09 轮换与补跑补充

计划轮换分为两步：申请轮换后不再领取新长任务，已运行长任务收尾期间继续按短任务配额采集；长任务全部结束或运行期限到达后，才关闭全部领取入口并排空当前任务。已准入但尚未返回的领取事务也受到保护，不能把已领取任务丢弃。异常退出、明确停止、租约心跳与运行期限保护保持原协议；此实现避免等待长任务期间的小时级停领，但最终短任务排空与进程重启仍会产生短暂间隙。

数据观察的当天补跑复用已成功坐标，成功坐标未到期不重新请求，只补到期失败或未完成坐标。当前实现仍会执行必要的元数据检查和存储维护，不能把“剩三坐标”等同于整轮只发生三次所有类型的请求。

人物日更原本在详情缓存命中后仍调用活动刷新，其新鲜分支也可能进入队伍及团本附加采集。原活动短任务只筛选活动到期的当前榜单角色，不能直接承担全部新鲜活动、样本和绑定角色的队伍更新；后续实现如下。

## 2026-11-09 人物附加采集拆分

人物日更保留资料与轻量活动字段的合并请求，随后保存已验证资料。队伍和已明确登记的团本来源不再在日更中同步发送HTTP，而是登记到持久化补采表。登记点沿用榜单、样本及绑定角色原来的活动刷新入口，不新增历史人物扫描。资料、样本资料仍由日更按阶段处理；Battle.net属性现已一起移入有界补采队列。

队伍按赛季和通关编号去重，同一通关记录被多个角色引用也只排一项；团本按赛季和人物身份去重，执行时继续校验当前Top20资格及原来源限制。队伍与团本沿用各自的事实缓存和重试时钟，成功资料不会等待附加采集完成。队列租约、输入版本和完成状态持久保存：进程中断后可恢复过期租约，旧工作者不能覆盖新租约或新输入的进度。相同输入再次登记不会重置成功缓存或失败冷却。

现有PlayerRaiderIOActivityMonitor负责消费，不新增线程或插件编号。每轮共享最多40次请求、90秒的新工作准入预算；先处理最多20项附加工作（45秒准入窗口），再刷新最多20个到期活动身份。队伍单项最多一次请求，团本单项预留最多三次请求，Battle.net单项预留认证及属性两次请求；正在执行的单项按原25秒请求超时收尾，因此90秒不是强制杀进程的总超时。日志与任务摘要包含附加工作成功/失败数、remaining_due、oldest_due_seconds及实际HTTP请求数。

有到期积压时，短任务最早在上次领取60秒后再次领取；无积压恢复原600秒频率，仍遵守两个短任务位及凌晨长任务优先规则。RIO的429冷却优先于其快速轮询，人物日更与这个补采入口共用数据库中的来源冷却，重建工作者不会绕过等待。Battle.net有到期候选时仍能领取短任务，RIO冷却期间只消费这个独立来源；调度检查实时队列，避免旧摘要挡住新登记候选。两天未再被登记的候选退出活跃队列，已有来源事实和队列记录保留；索引按状态和期限过滤，避免每轮反复消费历史人物。

上线需要先应用0266_character_enrichment_queue及0267_player_daily_checkpoint_and_freshness迁移，再重启后台加载新逻辑，并保持原活动短任务启用。本轮只在本地测试库执行迁移，未操作线上。上线验收应同时比较人物日更耗时与补采积压年龄，不能只把耗时移到后台队列就宣称整体更新更快。


## 2026-11-09 检查点与增量复核

人物日更按“专精资料、专精样本、绑定角色”保存持久化阶段检查点。只有资料成功写入且对应阶段没有失败，才记录完成；空榜单、资料身份不匹配、资料写入失败和样本补采失败均保留未完成。来源明确匿名的人物标为不可获取，不制造无限重试，也不伪造成功资料。领取时先写入当日启动标记，进程在进入采集前退出也不会丢失补跑资格。同日未完成任务最早30分钟后再领取，不受06:00限制；补跑仍占用长任务位。阶段完成后进程退出，只重做尚未保存检查点的阶段。

检查点绑定北京时间日期、赛季、构建、采集计划和相关天赋元数据版本；范围变化或跨日会重新建立批次。保存检查点时同时检查任务租约和批次代次，旧工作者不能发布新批次的进度。已完成的同日同范围任务不重复运行。这里是专精阶段检查点，不是每次HTTP后的事务日志；阶段中途退出可能重走该阶段，但已成功的来源缓存仍可复用。

资料缓存只比较来源实际提供的字段。缺少装备或天赋信号时，最长24小时重新核对；同时具备两类信号，且实际获取的资料连续验证一致后，复核间隔逐步延长到48、72小时。可用信号变化、赛季或构建变化会失效，失败不会刷新成功时钟。新增信号需要重新验证，不能靠一次缓存命中把未知内容认定为稳定。活动更新仍使用独立时钟。这项优化接受稳定资料最多72小时的复核延迟，并不承诺未提供变化信号的字段实时更新。

装备和天赋等预处理移到资料写入事务之前；写事务内重新加锁读取当前资料，保留短榜单拥有的排名与分数，以及独立补采更新的属性。重复候选先批量读取，只有新增、输入变化或接近过期的项才逐项加锁复核，避免重复登记通关记录造成大量无效写事务。

Battle.net候选按资料行应用，实际来源请求按角色身份的持久缓存去重；同一角色的不同专精仍共享成功时钟和失败退避。日更登记当前Top20及绑定角色，不遍历历史人物。补采复用批内认证令牌，OAuth请求也计入40次总预算；失败保留原属性。人物日更完成表示资料阶段完成及附加工作已登记，不代表所有附加属性、队伍与团本资料均已更新。

统计缓存新增同日正文校验证明。每次检查仍执行SQLite完整性检查，并重新散列压缩正文和全部行字段；只有当天已完整验证且字节、字段均未变的记录，才跳过解压及JSON校验。跨天、正文或元数据变化会重新完整验证，失败记录不得产生成功证明；零字节正文同样视为损坏。人工执行深检默认仍完整解压全部正文。维护结果新增verified_payloads、reused_payloads，分别表示本次完整校验与复用证明的正文数。

同日业务快照和历史记录未变、现有备份文件SHA-256也一致时复用备份；任何业务行变化或备份文件变化都重新备份，源正文校验失败仍不能覆盖好备份。轮次日志、校验证明和维护时间不作为业务数据变化，因此仅更新这些运行记录不会触发第二次备份；当日首次备份及业务变化后的备份仍使用原固定槽策略。增量检查仍会读取并散列正文，不是零磁盘开销。

验收需同时观察：人物checkpoint_reuse、各阶段耗时、实际HTTP量、资料缓存命中与失败数、补采remaining_due及oldest_due_seconds、统计verified_payloads/reused_payloads和备份reused。只有资料可见时间和积压年龄一起改善，才能确认整体更新效率提高；本地回归不代替线上完整日批次测量。


## 2026-11-09 层数范围收敛

按明确需求，层数只保留10–12层（含两端）、16层及以上、20层及以上。请求键分别为10-12、16-plus、20-plus，上游参数分别为(10,12)、(16,99)、(20,99)，其中99沿用来源接口的原有上界。页面、只读API、准备接口及命令行均使用这三种范围；自选层数入口关闭，旧链接指定已停用范围时明确提示，不偷偷换成另一份数据。

默认热图计划由38种层数降至3种：保持两个地区、两个时间范围及四种热图选项时，每个副本由608个组合降到48个，减少约92.1%。这是预设组合数的变化，不是整轮运行时间承诺；元数据、地图、其他模块、高级订阅及网络延迟仍有独立成本。

旧层数订阅不再加入待采集计划；旧层数完成记录导入文件计为跳过，避免旧范围一直让任务处于未完成状态。旧展示目录在读取时过滤已停用范围，后台增量或完整发布也会移除相应目录引用；旧正文与缓存文件保留，不执行删除。新的10–12层和16层及以上必须获取各自来源结果，不能用原10层以上结果替代；已有20层及以上的有效缓存可以继续复用。

本轮没有数据库模型或迁移变化，仅修改本地采集和展示逻辑。线上仍需后续部署及采集新范围才会生效。
