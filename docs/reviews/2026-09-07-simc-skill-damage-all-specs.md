# 全职业专精技能伤害复盘（2026-09-07）

## 结论及验收边界

已逐项检查全部 40 个专精，并构建、执行了真正的 SimC 导出程序。38 个专精通过基础配置的导出、单目标及 2/5/10/20 目标暴击期望和公式一致性检查；32 个拥有上游模板的专精也通过完整模板天赋检查。其余 8 个没有上游模板的专精使用基础输入，其中织雾武僧、神圣圣骑士被当前上游实现明确拒绝。

本次完成的是全专精复盘和共享生成链路修复，不能据此声称已经实现“40 专精全部技能、全部天赋组合、全部宠物机制”的完整伤害引擎。未部署、未推送、未修改用户的 `simc-source` 工作区，也未向业务数据库写入新快照。

## 已确认的根因及修复

1. **技能目录依赖默认循环。** 默认循环既会漏建技能，也会构造未选天赋的额外动作。现在导出入口固定等待循环，在原生动作初始化阶段按 DBC 技能书和已选天赋补全目录。无效 APL 注入测试中，38 个可导出专精的完整产物逐项一致。
2. **无效状态被强行激活。** 同职业其他专精的 buff、未选天赋以及模块设置为不可触发的 buff，原先仍被展开。现在先检查状态可用性，结果按 buff 缓存，再决定是否展开层数。
3. **前置排除之后仍进行事后全局推断。** 原生导出已声明全局状态，后端却仍按每层 buff 复制整份 actor、再按样本推断全局作用域。这会拖慢生成，也可能把局部效果重新放进全局表。新版数据直接使用前置声明，跳过旧的运行状态推断；旧格式兼容逻辑仍独立保留。
4. **逐行复制了随后丢弃的全部场景。** 展开某一行时，旧代码先深复制技能的全部层数，再清空。现在只复制该行需要的元数据和伤害分量。实际热点追踪确认，旧链路主要成本之一是这些 Python 深复制。
5. **多目标复用了同一个敌人。** 现在初始化独立目标池，通过技能自身的目标列表逐个取状态，不把主目标的减益、暴击条件复制到副目标；结束或异常时恢复目标状态。
6. **公式遗漏单目标也会生效的 AoE 钩子。** 导出并使用原生 AoE 修正项；直接伤害和周期伤害分别处理。暴击期望按每个分量、每个目标自己的非暴击和暴击贡献相加，不能一律乘 1.2。
7. **治疗、吸收、非伤害动作和辅助角色污染。** 这些动作在入口排除；增辉内部估算队友贡献的辅助角色不再作为玩家输出。补齐了萨满野性扑击的空法术指针回退。
8. **缺少计算条件却输出零。** 非有限数值、缺少触发上下文导致的零值被明确标为未解析；后端保留原因，页面提示列表存在覆盖缺口。

此前关于全局增伤前置排除、等伤害层数合并和暴击期望的修复一起纳入本轮验证。导出协议为 16，数据语义版本为 26，旧数据不能作为新版生成产物继续复用。

## 仍然存在的边界

- 织雾、神圣圣骑士：当前固定版本的 SimC 明确不支持，未通过绕过校验伪造可用数据。
- 宠物、守护者、累计伤害转化、残留伤害、部分武器依赖和需要血量基准的技能：独立玩家 AP/SP 探针不能证明其完整施法贡献。尤其不能因兽王或恶魔术能导出若干玩家技能，就宣称它们的宠物伤害已完整覆盖。
- 本轮使用基础配置和 32 份上游完整天赋模板，未穷举所有天赋组合、所有英雄分支和战斗触发路径；未执行生产数据库中全部逐天赋配置的重新生成。
- 仍使用原生职业代码处理硬编码机制，不是纯 DBC 计算引擎。仅解析 DBC 无法替代没有体现在数据表中的职业逻辑。
- 未做耗时对比；修复依据是调用链和热点分析。本地完整编译使用 Windows 适配，Linux 生产构建和线上页面数据重建尚未执行。
