# SimC 后台编译资源复盘

## 环境与结论

用户确认生产服务器为 2 核、8GB 内存，同时运行本项目完整业务。代码检查确认，已有的单任务默认值、`-O1` 和重型作业文件锁都不能约束整个编译进程树的内存峰值。此前没有操作系统级 CPU 或内存硬上限。

本轮没有读取线上内核 OOM 日志，不能据此认定每次故障都是编译器触发，也没有实测 Linux 编译峰值。以下是已证实的代码风险及本地修复。

## 已确认的问题

- 后台界面允许选择最多 8 个编译任务，管理命令只有下限，没有并发上限。
- 编译直接调用 `ninja -jN`，没有资源隔离。单个 C++ 编译进程仍可能申请大量内存。
- 固定审计版本中，仅 `sc_spell_data.inc` 和 `sc_spell_data_ptr.inc` 就分别约 29MB，默认同时编入。编译器还要处理语法结构、类型和优化，源码体积不能视为内存峰值；本轮没有关闭 PTR 数据以改变模拟功能。
- 上游 `BUILD_TESTING` 默认开启，旧代码构建全部默认目标，没有限定主程序 `simc`。
- 编译日志通过 `capture_output=True` 全部积存在调用方内存中。
- 普通子进程超时不等于整个编译进程树已经退出；Web 重启也可能留下原生编译进程。
- 后台异常处理曾把已有详细错误覆盖成笼统的“本地编译失败”。

## 已实现的限制（按用户要求放宽启动条件）

| 资源或行为 | 规则 |
| --- | --- |
| 编译并发 | 固定 `-j1`，旧客户端和命令行传入更大值也不能提高实际并发 |
| CPU | 整个编译作用域最多 1 核时间配额；2 核服务器上约为总计算资源的一半 |
| 内存预算 | `min(4GB, 物理或已读到的父级限额的 50%)`，不随瞬时可用内存收紧 |
| 内存回收阈值 | 作用域硬上限的 75%，8GB 主机约为 3GB |
| 启动门槛 | 删除固定可用内存门槛；内存紧张只记录提示，缺少 cgroup 元数据也不阻止启动 |
| swap | 作用域模式不允许使用 swap；兼容模式不宣称具备此限制 |
| 调度 | 尝试将 nice 增加 10；作用域模式额外降低 CPU 和 I/O 权重 |
| 进程与线程总数 | 作用域模式最多 64，兼容模式不设置用户级进程数限制 |
| 超时 | 整个编译作用域最多 3 小时，结束时清理本次作用域 |
| 构建目标 | 关闭测试构建与 LTO，只构建 `simc`，保留原有 `-O1` |
| 日志 | 直接写入项目 `.cache/simc-build-logs/`，失败只读取尾部；支持时记录 `memory.peak` 和 `memory.events` |

优先使用 systemd 临时 scope 和 cgroup v2，覆盖 CMake、Ninja、编译器、链接器及其子进程。普通用户通过用户级 systemd 管理器运行，不自动申请 sudo 或更改系统配置。启动编译器之前读取实际 `memory.max`、`memory.high`、`memory.swap.max`、`cpu.max` 和 `pids.max`，核验限制确实生效。

缺少 systemd、用户管理器、控制器委派或作用域限制核验失败时，使用兼容保护继续编译：在独立辅助进程中设置 `RLIMIT_AS`，限制每个进程的虚拟地址空间并由编译子进程继承；若已有更严格的进程限制则保留。兼容模式同时尝试绑定一个允许使用的 CPU、降低调度优先级，并保留固定单任务、日志落盘和超时清理。CPU 亲和性或 nice 设置不可用时只记录能力差异，不拦截启动。兼容保护不是整个进程树的总内存硬上限，也不是物理内存或 swap 配额。

辅助进程在任何资源核验、文件锁或构建命令之前写入本次唯一的启动标记。systemd 启动失败且辅助进程从未进入时，允许在父进程切换一次兼容方式；编译器报错、内存超限或超时不触发重编译。兼容模式建立独立进程组，超时清理整组。子进程继续持有独立编译锁并向原生构建进程传递锁描述符，避免父进程退出后重复编译。

## 验证及边界

- 17 项资源策略及失败路径测试通过，覆盖低可用内存仍可启动、缺少 cgroup、父级限额、systemd 用户管理器不可用、进程限制继承、兼容模式超时清理，以及真实编译失败后不重复执行。
- 1 项命令集成测试确认传入更高并发仍只走统一构建入口，与资源测试共 18 项通过；在 Windows 下只替代 `fcntl` 导入，不据此宣称验证 Linux 文件锁语义。
- Django 系统检查、JavaScript 语法和差异空白检查通过。
- 本机没有可运行的 Linux/systemd 环境，未进行实际 cgroup OOM 压测、生产编译或线上部署。首次线上执行还需验证用户管理器及控制器可用性。
- 4GB 是当前 8GB 主机的折中预算，不是已证实足够完成全部 SimC 源文件编译的容量。作用域模式限制总内存，兼容模式限制各进程地址空间；两者不能混为一谈。超限失败不会触发自动加大预算重试。
- 此次限制针对原生编译阶段。其后的模板/APL 同步和技能快照生成沿用原有链路，不应把整个后台维护流程都宣称为已受此内存上限保护。
- 已取消启动时强制预留 2GB 可用内存。繁忙时允许触发编译不代表主机不会 OOM；尤其兼容模式没有进程树总内存上限，仍需要观察实际峰值。
