# 每日聚合存储复盘与优化

## 结论与证据边界

问题确实包含设计缺陷：之前把完整展示对象直接作为中间缓存及发布正文保存，重复展开节点、布局、天赋方案，既没有体积预算，也没有完整的中间缓存生命周期。历史回收还存在预算不足时不能前进、发布使检查点失效等问题。文件化只改变存储介质，不会自动获得合理的数据模型。

本次先同步到已上线提交 `8262f7a2`。用户提供的《WCL排名写放大复盘与优化》记录的生产证据继续有效：排名快照跨天换人、换战斗及一次天赋身份修正造成写放大，不能归因为人物资料每天覆盖排名，也不能撤回正确的天赋身份修复。本轮没有重复修改已上线的排名差量、天赋紧凑化和磁盘门禁。

以下生产数字来自用户提供的盘点，尚未从本环境独立读取生产主机：

| 指标 | 数值 | 含义 |
| --- | --- | --- |
| 02:26—05:56创建且仍存在的统计文件 | 1.93 GiB | 与此阶段磁盘增长直接相关 |
| 同期磁盘净余量下降 | 2.27 GiB | 包含其他进程，不能全归因于统计 |
| 同期binlog净增 | 约124 MB | 这一阶段不再是主要增长来源 |
| 中间缓存重写 | 1.63 GiB | 固定路径替换，属于写入流量，不等于净增长 |
| 当前40专精引用的统计版本 | 1.92 GiB | 当前版本本身也需要瘦身 |
| 非当前历史版本 | 9.54 GiB | 约为当前版本的5倍 |
| 超过48小时宽限的历史 | 5.85 GiB | 仍须扣除回退保护、内容异常和未确认归属，不能直接全部删除 |

本地没有这些生产大文件，公开媒体路径也不可读取；不能把本地盘点、历史样本回放说成生产全量验收。

## 数据为什么会变大

### 输入到输出的放大量化补充

用户进一步澄清：所问约2GiB是此前40专精当前版本合计1.92GiB，重点是当前结果为何比角色原始数据大，历史堆积不是这个问题的解释。

对已有40专精120条样本补算相同UTF-8紧凑JSON口径：角色天赋输入1,361,954字节，共享天赋元数据2,381,022字节，完整聚合输出24,111,019字节。其中 `talent_popularity_tree` 合计21,102,919字节，占87.52%。输出约为角色天赋输入的17.70倍；把共享元数据也计入输入后，约为6.44倍。该样本证明展示模型展开具有明显写放大，但不是生产1.92GiB的字段占比实测。

具体链路是：角色选择事实先结合全量天赋元数据，生成完整树底板，加入名称、说明、选项、坐标、连线及节点样本，再同时输出 `nodes`、`trees[].nodes`、`tree_set`、`layout` 和树内 `panel`。这套结构在每个专精的不同副本、首领和难度范围重新保存；大秘境总览还有独立统计树。JSON不保留内存中的共享引用，所有嵌入结构都会实际重复落盘。

第一阶段的无损编码只去掉单个详情内部的重复，59.4%的缩减没有完成资料引用分层。用户指出已有数据库资料不应重复保存后，第二阶段已改为引用现有数据库中的名称、图标和描述，并由单份树节点事实与统计差异重建展示布局；没有新增一份大型静态资料文件。但线上1.92GiB的实际字段分布仍未直接读取，不能声称已逐字节归因。

1. **同一节点存在多种展开表示。** 天赋统计保存平铺节点、按树节点、原始树集合、布局节点、面板和连线；其中有完全相等的重复对象，也有只增加坐标或使用率的另一种表示。普通JSON不保留内存共享引用，每出现一次就重新写一份。
2. **同一方案出现在多个视图。** 全部方案、方案族、族代表、主模板和模板族会重复嵌入完整方案及差异。长描述、导入码、字段名也被重复写入。
3. **工作缓存与发布副本叠加。** 按范围的计算检查点用于恢复失败计算，最终发布另存完整版本；发布保留当前和回退版本本身有价值，但没有及时回收会不断叠加。WCL周期在指纹中，分页缓存文件名不随日期增长。
4. **读写过程有内存放大。** 原写入同时生成整块JSON文本、UTF-8字节并再次反序列化；读取复制正文切片；计算摘要再序列化整块对象。这些临时副本会使峰值内存高于文件体积。尚未测量生产进程RSS，不把磁盘占用称作已确认的内存泄漏。

## 已实现的底层修改

### 统计数据与页面结构分离

- 方案只保存一份，主模板和分组使用引用。
- 新格式只保存一份树节点事实、构建状态和统计差异；平铺节点、分树节点、面板和连线在读取时由现有渲染器生成，不再全部落盘。写入前逐项比较重建结果，不能证明等价的旧结构保留兼容路径。
- 名称、图标和描述优先引用已有 `WowTalentNodeMetadata` 与中央技能展示资料。引用绑定具体元数据版本、职业专精和节点行身份；读取时验证版本和节点身份，允许继续引用退役节点，不以当前默认版本替换旧身份。
- 有真实资料引用的详情读取为两次批量SELECT：节点资料及中央技能展示资料；200处重复引用仍为两次查询。没有写库、联网或逐节点查询，同一次发布中的多个详情复用目录查询结果，发布结束即释放。
- 节点ID、点数、选择、计数以及重建旧结构所需的少量坐标和结构事实保留；中央名称、描述修正可以更新展示，但不能改变历史统计。缺失或身份冲突的引用拒绝使用，不静默套用另一节点。
- 同一结果中的玩家摘要只保存一份，节点使用率和方案通过局部索引引用，不反复嵌入角色名称、服务器、DPS等整份摘要。
- 节点使用字段表加行数据，字段名不在每个节点重复写入；保留不同结构及未知字段。
- 不属于可确认数据库资料的业务字符串保留原值；重复字符串仍可使用局部文本表，不能凭字段名删除未知内容。
- 只有能严格证明等价的结构才转换；无法匹配时保留原表示。页面读取仍获得原有完整结构，统计样本、计数、点数、选择、来源、布局、文本及全部方案都不删减。
- 旧JSON保持只读兼容。新发布指纹改变，下一次聚合可切换紧凑表示；旧发布仍受正常回退策略保护。

### 中间缓存的成本控制

- 私有文件改为流式gzip，后缀为 `.json.gz`，读取仍支持旧 `.json`。
- 每个业务范围仍只有一个最新路径及一个固定暂存文件，发布使用旧版同一把跨进程锁，原子替换失败保留旧结果。
- 默认单项解压及编码预算64 MiB，超限不写入缓存，保留已计算结果；读取超限拒绝复用。预算是缓存护栏，不是裁剪业务数据。
- 缓存正文摘要在编码过程中计算，读取通过字节视图校验；消除整块编码后再解码的规范化过程。
- 冷缓存缺失默认不再回查旧大JSON表。仅显式设置 `SPEC_AGGREGATION_IMPORT_LEGACY_DATABASE=True` 时按需导入旧表；没有执行全表迁移或清空旧表。
- 默认7天未更新的可识别中间文件分批回收，最低保留2天；保留锁文件。未知、损坏、链接及不可确认归属的文件只报告，不冒充可删除缓存。
- 单项预算与TTL并不构成整个文件系统的硬配额；固定范围数量、实际总量仍由诊断输出监测。

### 发布与回收

- 发布采用紧凑JSON和流式计量，默认单详情64 MiB；超限发布失败并保留旧入口，不写出数GiB单项文件。
- 合并远端回收修复后，历史版本数、详情总数和已验证检查点不再套用512个的批次上限；单代目录仍按结构限制，实际JSON读取默认每轮最多512次，字节预算与单项读取上限独立控制。历史目录身份盘点随实际规模增长。
- 单个详情大于每轮64 MiB时，允许在独立256 MiB单文件安全上限内完成一次校验，再通过签名检查点续传，避免一直暂停。
- 校验检查点按文件身份复用。发布新版本或移除其他旧文件，不会让未变化历史的证明全部失效；变化、替换、密钥轮换和伪造签名仍使对应证明失效。当前清单、入口和删除前目录检查不省略。
- 当前版本及每个模块最近两个历史版本继续保护，退休时间和文件修改时间都必须经过48小时宽限。
- 聚合历史与中间缓存的后台回收默认启用；现有显式关闭设置仍有效。其他领域保留原有开关。回收日志补充实际删除字节、暂停范围和原因。
- 禁用标记不自动忽略。新增显式修复入口，先完整验证当前、历史、孤儿和未完成删除意图，再重建一致清单并归档禁用原因；修复本身不删除历史文件。异常或未知内容仍拒绝修复。

## 生产只读核验与受控回收

在生产项目目录使用该项目Python环境执行。以下首组命令只读取文件，不删除业务数据：

```text
python manage.py audit_aggregation_storage
python manage.py maintain_aggregation_storage --kind published
python manage.py maintain_aggregation_storage --kind work
```

盘点按当前引用、回退保护、宽限内历史、退休超过48小时待校验、未登记历史或失败发布分类，并输出禁用原因和最大的文件；同时检查媒体目录、项目私有目录、来源缓存、日志、`botend/data` 和 `tmp`。根目录可能相互包含，不能把各根目录合计直接相加。未知路径不推定为垃圾；项目目录之外的MySQL数据文件仍需在主机侧另行核对。

对最大统计详情使用 `audit_aggregation_storage --detail <聚合根目录内的实际详情JSON路径>`，可得到字段体积分摊及无损转换对比。单文件超过256 MiB会明确拒绝，需要单独分析，不能强行加载或清空。

确认结果后，显式应用命令为：

```text
python manage.py maintain_aggregation_storage --kind published --apply --scope-limit 40 --passes 16
python manage.py maintain_aggregation_storage --kind work --apply --passes 16
```

输出的 `has_more` 与各范围 `paused` 表示仍有后续工作；总轮数有界，不承诺一条命令清完所有历史。存在禁用范围时，先以 `--repair-disabled-scope <赛季/职业/专精>` 预演；只有完整校验通过才添加 `--apply`，需要跨轮校验时可指定 `--passes`。禁止手删禁用标记、清单或当前入口来绕过验证。

本轮未连接生产主机、未部署、未删除生产文件，也未修改MySQL或系统配置。未知十几GiB数据文件的真实归属，以及线上回收器的具体错误原因，仍须用上述盘点与日志确认。
