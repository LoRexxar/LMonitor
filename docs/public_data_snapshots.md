# 公共数据 JSON 快照优化：评估与实施

## 结论与范围

适合预生成的数据应满足：所有访问者看到相同内容、生成成本高于读取成本、更新有明确时机、允许短时间继续展示上一版。分片后的公共展示结果交给浏览器筛选，原始数据库继续作为业务事实来源。

已完成配装目录试点、统计页、冒险手册掉落优化，以及 Mythicstats 统一后台采集发布。强化适用性、用户配装和实时状态继续沿用原接口。本次未提交、推送或部署生产。

| 页面或数据 | 当前代码行为 | 建议与优先级 |
| --- | --- | --- |
| 配装器装备候选目录 | 每次搜索、来源切换、分页都会读取本赛季整批装备变体，做职业适配、分组和 Tooltip 投影 | 首批已实施。按职业、专精、槽位分片，浏览器筛选和分页 |
| 专精大米、团本详情 | 已有聚合 JSON，但读取时还会刷新装备和天赋；部分旧格式或缺失字段触发实时统计 | 第二批已实施只读聚合文件，汇总及展示补全统一后台生成；仍沿用每个专精的既有文件，后续可按首领继续拆分 |
| 专精人物榜、概览模块 | 已读取聚合文件，并缓存概览的精简投影 | 中优先级。复用现有文件，补齐展示版本和生成通知，不再建一套同义缓存 |
| 全职业入口 `/portal/specs/` | 主要是职业导航页面，不执行大型统计 | 无需单独静态化 HTML；优化其进入后的实际数据模块 |
| 全职业大秘境 DPS 排行 | `mplus_dps_rankings_service.py` 已有后台发布、前台读文件路径 | 保留，统一监控新鲜度和文件失效处理即可 |
| Mythicstats DPS 接口 | 已统一后台采集全部副本、单副本与最近三个周次，公开接口只读发布文件 | 第三批已实施。当前赛季、来源口径、榜单均来自同一发布路径 |
| 冒险手册装备列表 | 每次筛选会读取首领载荷、合并掉落、补职业专精规则、名称图标和已缓存 Tooltip | 第二批已实施。按发布版本、副本、难度及资料分支分片；前端筛选；缺失 Tooltip 仍按需补充 |
| 冒险手册技能详情 | 发布版稳定，但存在职责、难度、首领和动态文本条件 | 适合按首领与难度投影；不把整部手册合并成一个大文件 |
| 公共强化字典 | 来源稳定，但可选性依赖装备、制造配方、专精、插槽等规则 | 可预生成字典，适用性和最终选择仍由后端校验；本批未改 |
| 用户保存配装、已有装备、运行状态、管理权限 | 用户隔离或实时状态 | 不放入公共静态文件，继续使用现有认证和动态接口 |

以上判断来自当前工作区代码，不代表已采集生产流量或完成线上 SQL 性能剖析。

## 首批实现

参考 `simc_benchmark_result_snapshot.py` 的文件锁、原子写入、独立维护和失败保留机制。新服务是 `botend/services/gear_catalog_snapshot.py`。

1. 页面首次请求固定的职业、专精、槽位坐标。坐标必须通过现有白名单校验，搜索词不进入文件名，也不会制造无限数量的缓存键。
2. 请求只登记一个很小的持久请求文件、读取发布索引并传输 JSON 文件，不查询装备数据库，也不回退同步聚合。
3. 监控后端启动独立维护线程，每轮最多构建 4 个分片，轮次间隔 15 秒；跨进程文件锁避免重复构建。常规采集线程不被构建阻塞。
4. 后台复用现有职业适配、主属性、武器栏位、正式服/PTR 分支身份、来源、属性和 Tooltip 规则。客户端只执行公开候选集上的筛选和分页。
5. 先写完整 JSON 和 gzip，再原子替换发布索引。构建失败保留上一版；构建期间源指纹变化则不发布。首次没有文件时返回 202，页面显示准备中并有限重试，不伪装成无装备。
6. 正文按不可变版本保存，HTTP 支持 ETag、304、60 秒公共缓存和 gzip 预压缩。浏览器缓存最多 6 个坐标、60 秒；同坐标并发请求合并。来源筛选、隐藏属性、搜索、分页都在本地执行。
7. 翻页时若文件换代，从第一页重新显示，避免将新旧顺序拼接。迟到的旧槽位请求不能覆盖当前槽位。
8. 内容指纹相同就复用原版本，避免无变化时生成新文件或让浏览器重复下载。

为了保持兼容，原 `/portal/api/gear-builder/catalog/` 的分页协议仍保留；配装器页面使用同一接口的 `snapshot=1` 分支。其他旧调用方仍可能访问数据库，不能将目录读取的零查询描述为整站零查询。页面初始化、用户操作、分析中间件等也不在零查询承诺范围内。

## 更新与运行

默认文件根目录为项目下 `var/gear-catalog`。可通过已有主机配置中的 `GEAR_CATALOG_SNAPSHOT_ROOT` 指定共享路径，本次没有改动配置文件。Web 与监控后端必须访问同一目录；多机器部署应提供共享文件存储，否则某台机器生成的文件无法被另一台读取。

后台空闲轮次只检查小文件，数据库指纹降为每 5 分钟检查一次；新分片和显式更新通知立即唤醒。缺文件优先，同级按最近访问排序，失败分片延后重试。后台用赛季目录状态、装备与变体的数量/最大更新时间、显式更新通知检测变化；大版本或中央装备更新会发送事务提交后的通知。每个已请求坐标最长间隔 12 小时重新核验一次内容，补偿没有更新时间的旧写入方式。

新增或维护导入器时，必须更新 `updated_at`，或者在发布事务内调用 `invalidate_catalog_snapshots()`，由它在提交后写入通知。只通过 SQL 修改字段且不更新时间、也不通知，会延迟到周期核验才更新，不保证立即可见。后台停机期间继续提供上一版；大量分片排队和浏览器缓存也会带来更新延迟。

修改投影字段或筛选契约时应递增服务中的 `SCHEMA_VERSION` 并同步发布前端脚本，确保旧文件不被新协议误读。

发布新页面前应预热常用职业专精，减少首次准备等待。以下命令使用运行环境原本的 Django 设置：

```powershell
# 预热战士狂怒全部槽位
python manage.py refresh_gear_catalog_snapshots --class Warrior --spec Fury

# 只预热一个槽位
python manage.py refresh_gear_catalog_snapshots --class Warrior --spec Fury --slot head

# 刷新已被请求的分片
python manage.py refresh_gear_catalog_snapshots

# 对已请求分片重新计算；内容相同会复用原文件
python manage.py refresh_gear_catalog_snapshots --force
```

正常监控后端启动时自动启动维护线程。只运行 Web 开发服务器不会自动启动该线程，需要先运行上述命令，或在独立维护进程周期执行刷新命令。首次文件尚未生成、后端停机时，页面最多自动重试约一分钟，随后给出稍后重试提示。

保持数据库与已有批次不变即可回退：恢复页面原来的目录加载脚本、继续使用旧分页协议，不需要回滚数据迁移。本次没有新增数据库迁移。

历史快照和中断构建留下的文件予以保留，不自动删除；无变化时不会新增正文版本。有真实数据更新时仍会产生新版本，应监控目录体积并另行制定经确认的归档策略。

## 第二批实现与更新顺序

### 专精大米、团本统计

- 公开详情请求不再调用汇总、单本或首领重算，也不再刷新装备与天赋。缺失或损坏文件显示现有空状态，旧版文件继续读取；不会用请求回源补算。
- 后台 `SpecDetailAggregationMonitor` 同时生成大米各本与全部副本汇总，再统一补全装备、天赋和生成时间。汇总继续使用原始样本合并口径，不能平均各副本的平均值。
- 手工命令与定时任务共用生成器；团本两种难度都生成，指定赛季的人物榜也使用所选赛季。
- 生成与展示补全全部成功后原子替换文件。装备和天赋更新仍通过既有更新队列触发监控任务。
- 统计概览缓存增加文件身份、大小和路径判断，避免文件原子替换但修改时间相同时误用旧缓存。
- **切换新代码前必须先预生成新统计文件**，否则旧文件没有 `summary`，大米汇总会暂时显示空状态；其他旧字段也需本次生成后更新。

### 冒险手册掉落

- 新服务 `journal_loot_snapshot.py` 以发布版本、副本、难度、资料分支与构建信息区分文件，根目录默认 `var/journal-loot`，可使用 `JOURNAL_LOOT_SNAPSHOT_ROOT` 指定共享路径。
- 后台生成完整掉落、来源首领、中文名称、图标、职业专精资格以及已缓存的装备属性特效。复用现有分支和资格规则，不改手册发布载荷或装备事实。
- HTML 从文件读取完整副本列表，浏览器直接隐藏不匹配行，搜索和六类筛选无需重新请求列表。URL、难度表单和首领链接同步保留当前筛选；禁用 JavaScript 时 GET 筛选仍可用。
- 兼容 JSON 接口仍返回筛选结果，读取文件，不再查询装备表补全。页面仍有发布指针、副本、首领和赛季的基础查询，不能称作页面零查询。
- 首次文件缺失时只登记任务并提示准备中；浏览器每 3 秒检查准备状态，最多 20 次。后台停机不会退回同步计算。状态接口只返回准备状态。
- 监控后端独立线程每 15 秒处理最多 4 个分片，文件锁避免多个进程同时生成。空闲时不查数据库，数据通知、新任务唤醒，漏通知每 5 分钟检查；每个分片至少每小时重新核验，补偿详情缓存新增。
- 失败保留当前坐标的上一版；构建期间装备源变化不发布。版本、分支和难度不共用旧文件。数据源更新后，浏览器已打开的页面在重新加载时获取新版。
- 不完整的逐件详情仍使用原来的补充接口；只加载可见行、并发不超过 4，同页共享请求结果。已具备详情的列表过滤没有网络请求。

## 第三批：Mythicstats 单一采集发布路径

原先定时任务仅采集全部副本汇总，页面遇到单副本或缺失周次会自行抓取；默认赛季也在请求中检测。现统一为：定时任务或手工命令调用同一个采集服务，事务保存数据库，准备不可变 JSON，最后原子替换发布索引，公开接口只读已发布文件。

- 采集器从真实上游识别当前赛季、副本目录、最近三个周次，覆盖全部副本汇总、每个单副本和输出、坦克、治疗三种职责。当前周每次刷新，历史周成功分片复用，缺失、失败或旧数据库导出的历史分片重新采集。
- 赛季归属由来源周次决定；配置赛季仅作校验，不允许把当前榜单重新标记成其他赛季。跨赛季的历史周次不会混入新赛季。
- 当前赛季、周次、副本目录和来源层数口径持久保存在文件中。页面不再检测上游赛季、不查榜单表、不补抓、不写库，也不通过访问创建采集任务。
- 三种职责在同一数据库事务内保存，防止半份榜单。更新失败保留同赛季、同副本、同周次的旧文件；页面显示更新未成功提示。首次缺失显示“数据尚未准备好”。发布索引失败保留之前的完整发布索引。
- 后台和手工命令共用文件锁，避免重复采集。默认根目录为 `var/mythicstats`，可通过 `MYTHICSTATS_SNAPSHOT_ROOT` 指定共享位置；Web 与监控进程必须读取同一目录。历史文件保留，不自动删除。
- 继续使用已有 `PortalMythicstatsDpsMonitor` 调度和间隔，目标建议为 `auto`。只运行 Web 服务时需要独立调度刷新命令。没有修改系统配置或新增数据库迁移。
